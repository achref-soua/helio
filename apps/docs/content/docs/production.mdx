[Self-hosting](/docs/self-hosting) covers local and single-box deployments. This
page is the production path: a managed Kubernetes cluster, the
[Helm chart](https://github.com/achref-soua/helio/tree/main/infra/helm/helio),
and managed datastores.

## Choosing a topology

| Topology          | Good for                 | How                                            |
| ----------------- | ------------------------ | ---------------------------------------------- |
| Cloud VM          | The fastest hosted start | paste the cloud-init file when creating the VM |
| Docker Compose    | A single VM / evaluation | `docker compose --profile full up -d`          |
| Kubernetes (Helm) | Production, scaling, HA  | the `helio` Helm chart + managed datastores    |

The cloud-VM path is below; the rest of this page walks through the Kubernetes
path on a managed cloud.

## Deploy on a cloud VM (one paste)

The lowest-friction hosted deploy: spin up a Linux VM at any provider
(DigitalOcean, Hetzner, Vultr, Linode, AWS EC2, Google Cloud, Azure, …) and
paste one file into its **User data** / **Cloud-init** / **Startup script** box.
On first boot the VM installs Docker and Helio and serves the dashboard at
`http://<your-server-ip>:3000` — no SSH, no Docker knowledge.

1. Create a VM. **4 GB RAM** for the default `core` profile, **8 GB** for
   `--full`. Ubuntu or Debian is the smoothest base.
2. Paste
   [`infra/cloud/helio-cloud-init.yaml`](https://github.com/achref-soua/helio/blob/main/infra/cloud/helio-cloud-init.yaml)
   as the instance's user data. It detects the VM's public IP, sets `APP_URL`
   to it (so logins work — the dashboard checks the request origin), and runs
   the installer non-interactively.
3. Open inbound **TCP 3000** (dashboard) — and **4000** if you use the REST API
   — in the provider's firewall / security group.
4. Browse to `http://<your-server-ip>:3000` and create the first account; it
   becomes the administrator. (First boot takes a few minutes while images
   pull.)

Manage it afterwards over SSH like any install: `~/.helio/helio status | logs |
update | stop`. To put it behind a domain with HTTPS, point an A record at the
VM, terminate TLS with a reverse proxy (Caddy/nginx/Traefik) or the provider's
load balancer, and set `HELIO_APP_URL=https://your-domain` before installing (or
edit `APP_URL` in `~/.helio/.env` and run `~/.helio/helio stop && ~/.helio/helio start`).

## Managed-cloud walkthrough

The shape is the same on any managed Kubernetes (GKE, EKS, AKS, DigitalOcean,
Hetzner, …): a cluster, managed Postgres and Redis, and the chart.

### 1. Provision the cluster and datastores

- A managed **Kubernetes** cluster (3 small nodes is plenty to start).
- A managed **PostgreSQL 16** with the **pgvector** extension available
  (Helio stores embeddings there). Create a database and note the connection
  string.
- A managed **Redis** (or in-cluster — see below).
- For the full event/analytics loop, reachable **ClickHouse**, a
  **Kafka-compatible** broker (Redpanda/MSK), **Temporal**, and **S3** — deploy
  these from their official charts/operators or use managed equivalents.

<Callout type="info">
  Helio creates its row-level-security role (`helio_app`) during migration, so your managed Postgres
  only needs the standard admin user up front — the migration job provisions the rest.
</Callout>

### 2. Create the namespace and secrets

Keep secrets out of values files. Create a Kubernetes Secret out-of-band and
reference it from the chart:

```bash
kubectl create namespace helio

kubectl --namespace helio create secret generic helio-secrets \
  --from-literal=BETTER_AUTH_SECRET="$(openssl rand -hex 32)" \
  --from-literal=TRACKING_SECRET="$(openssl rand -hex 24)" \
  --from-literal=UNSUBSCRIBE_SECRET="$(openssl rand -hex 24)" \
  --from-literal=DATABASE_URL="postgresql://helio_app:...@db-host:5432/helio" \
  --from-literal=DATABASE_ADMIN_URL="postgresql://admin:...@db-host:5432/helio" \
  --from-literal=REDIS_URL="rediss://...:6379"
```

### 3. Write production values

```yaml title="values.prod.yaml"
image:
  tag: '0.8.0'

secrets:
  existingSecret: helio-secrets

# Use managed datastores, not the bundled eval ones.
postgresql:
  enabled: false
redis:
  enabled: false

config:
  APP_URL: https://app.acme.com
  PUBLIC_TRACKING_URL: https://track.acme.com
  CLICKHOUSE_URL: http://clickhouse.data:8123
  KAFKA_BROKERS: redpanda.data:9092
  TEMPORAL_ADDRESS: temporal.data:7233

ingress:
  enabled: true
  className: nginx
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
  hosts:
    - host: app.acme.com
      paths: [{ path: /, pathType: Prefix, service: web }]
    - host: api.acme.com
      paths: [{ path: /, pathType: Prefix, service: api }]
    - host: track.acme.com
      paths: [{ path: /, pathType: Prefix, service: tracking }]
  tls:
    - secretName: helio-tls
      hosts: [app.acme.com, api.acme.com, track.acme.com]

autoscaling:
  enabled: true
  services: [web, api, ingest, tracking]

# Run schema migrations as a pre-install/upgrade hook. Point at an image that
# bundles @helio/db and the Prisma CLI.
migrations:
  enabled: true
  image: ghcr.io/achref-soua/helio-web:0.8.0
```

### 4. Install

```bash
helm install helio ./infra/helm/helio \
  --namespace helio \
  --values values.prod.yaml
```

Helm runs the migration job first (creating the schema and the `helio_app`
role), then rolls out the services. Watch it:

```bash
kubectl --namespace helio get pods -w
```

### 5. DNS and TLS

Point your `app`, `api`, and `track` DNS records at the ingress controller's
external address. With [cert-manager](https://cert-manager.io/) and the
annotation above, certificates are issued automatically for the `tls` hosts.

## Connection pooling

At scale, route the RLS app role (`helio_app`) through a transaction-mode
PgBouncer so many app connections share a few Postgres backends. The admin
connection (migrations, the auth kernel) stays direct. The Compose bundle ships
an opt-in `pgbouncer` service — enable it in your `.env`:

```bash
COMPOSE_PROFILES=full,pgbouncer
HELIO_APP_DB_HOST=pgbouncer
HELIO_APP_DB_PORT=6432
INTEL_DATABASE_PGBOUNCER=true   # asyncpg disables its statement cache for the pooler
```

This is safe because every tenant query sets `app.org_id` transaction-locally,
so row-level security is enforced identically with or without the pooler — see
[ADR-0022](https://github.com/achref-soua/helio/blob/main/docs/adr/0022-pgbouncer-transaction-pooling.md).
On Kubernetes, run PgBouncer (transaction mode) as a Deployment and point
`DATABASE_URL` at it while leaving `DATABASE_ADMIN_URL` on the direct service.

## Observability

Set `config.OTEL_EXPORTER_OTLP_ENDPOINT` to your collector to turn on
distributed tracing; every service emits OpenTelemetry traces and structured
logs, and exposes Prometheus metrics. See the
[architecture](/docs/architecture) for the trace boundaries.

## Production checklist

- **Secrets** managed out-of-band (`secrets.existingSecret`), not in values.
- **Datastores** managed (`postgresql.enabled=false`, `redis.enabled=false`),
  with backups and PITR on Postgres.
- **TLS** terminated at the ingress; HTTP redirects to HTTPS.
- **Autoscaling** enabled for the request-serving services.
- **Tenant isolation** is enforced by Postgres RLS regardless of deployment —
  see [Tenancy](/docs/concepts/tenancy).
- **Deliverability** — configure SPF/DKIM/DMARC for your sending domain and use
  a reputable relay (SES/Postmark/Resend) rather than raw SMTP; point its
  bounce/complaint webhook at the gateway
  ([setup](/docs/guides/deliverability#bounces--complaints)).
- **Rolling deploys are safe** — every service drains on SIGTERM and journeys
  resume across worker restarts.

Day-2 procedures — backups and restore drills, upgrades, secret rotation,
incident quick checks — live in the
[production operations runbook](https://github.com/achref-soua/helio/blob/main/docs/runbooks/production-ops.md).

## Running a public demo

A try-it-yourself instance lets people explore Helio before self-hosting. The
trick to a _public_ demo is that visitors must be able to break things without
breaking it for the next visitor — so a demo resets itself to a known state on a
schedule, and never sends real email.

### On a single VM (one paste)

The fastest path. Paste
[`infra/cloud/helio-demo-cloud-init.yaml`](https://github.com/achref-soua/helio/blob/main/infra/cloud/helio-demo-cloud-init.yaml)
as a Linux VM's user-data (4 GB RAM is plenty for the demo's `core` profile). On
first boot it installs Helio and installs a cron that restores a **golden
snapshot** every 6 hours.

The reset reuses Helio's own backup/restore (a full `pg_dump` / `pg_restore`),
so the snapshot captures everything — the demo login and the sample data
included — and a restore reverts any visitor changes. One-time setup after the
VM is up:

1. Open `http://<server-ip>:3000` and **sign up the demo admin** with the
   throwaway credentials you'll publish (e.g. `demo@helio.test` / `demo-helio`).
2. On the setup screen, **load sample data** so the demo has content.
3. Capture that state as the golden snapshot the cron restores:

   ```bash
   ~/.helio/helio backup
   cp ~/.helio/backups/$(ls -t ~/.helio/backups | head -1) ~/.helio/backups/demo-golden.dump
   ```

Until `demo-golden.dump` exists the reset is a safe no-op, so there's no rush.
Adjust the cadence by editing the VM's crontab (`helio-demo-reset` runs the
restore). To refresh the demo's content later, repeat step 3.

### On Kubernetes (Helm)

Deploy the chart with the bundled eval datastores. A ready-made overlay lives at
[`infra/helm/helio/values-demo.yaml`](https://github.com/achref-soua/helio/blob/main/infra/helm/helio/values-demo.yaml):

```bash
helm install helio-demo ./infra/helm/helio \
  --namespace helio-demo --create-namespace \
  --values ./infra/helm/helio/values-demo.yaml \
  --set secrets.data.BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

Reset it on a schedule by restoring a golden snapshot (a `CronJob` running the
backup image's `restore`) or by redeploying.

<Callout type="warn">
  A public demo is internet-exposed and shared. Keep it isolated (its own VM / namespace), reset it
  on a schedule, leave email on the bundled test inbox (no provider configured = no real sends),
  keep the AI provider key out of it unless you intend to pay for usage, and never point a demo at
  production datastores.
</Callout>
