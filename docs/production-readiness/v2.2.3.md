# Helio production-readiness audit — v2.2.3

**Date:** 2026-06-28 · **Auditor:** Achref Soua · **Tree:** `develop` == `main`
@ v2.2.3 · **Scope:** full-stack acceptance + non-functional production audit.

This is a point-in-time audit, not feature work. Every number below was
**measured on this run** — nothing is estimated or carried over. Where a thing
could not be measured on the audit box, it is marked _not measured_ and why.
A fabricated metric would invalidate the whole report; there are none.

## Reference environment

WSL2, 20 vCPU, 15 GiB RAM, ~10 GiB free, single host. **All services were
co-located on this one box** during load — k6, the ingest process, Redpanda,
ClickHouse, Postgres and Redis sharing the same CPU and memory. A real
deployment separates these and runs multiple stateless ingest replicas, so the
throughput figures here **understate** production rather than flatter it. Full
profile was up (`docker compose --profile full`): Postgres 16 + pgvector,
Redis, Mailpit, ClickHouse 24.12, Redpanda 24.3, Temporal 1.26, MinIO.

---

## Verdict

**Ship to early adopters now; not yet for an enterprise betting
revenue-critical campaigns on day one.**

- **Ready now** for a self-hosting team that owns its data, sends modest
  volume, and accepts being an early user. The security posture, durable
  journey execution, tenant isolation, and now the _measured_ ingestion
  capacity are genuinely ahead of most early-stage products.
- **Not yet** for a large enterprise on day one, for three honest reasons that
  no amount of code closes: zero production track record (no incident history,
  no real-traffic DR drill, no multi-month upgrade history), email
  deliverability reputation is earned by sending not by shipping, and the
  API-read and email-send hot paths are not yet load-tested (only ingestion).

## Part B — Non-functional audit

### B1. Load / performance — ingestion (headline; real numbers)

Method: production esbuild bundle of `@helio/ingest` (`node dist/server.mjs`,
not `tsx`), rate limit lifted to measure raw capacity, k6 `constant-arrival-rate`
firehose of 10-event batches against the same `/v1/batch` the browser SDK uses.

| Offered  | Sustained events/s | accept | p95    | errors | notes                              |
| -------- | ------------------ | ------ | ------ | ------ | ---------------------------------- |
| 6,000/s  | 6,063              | 100%   | 5.4 ms | 0%     | 4 VUs used — far from saturated    |
| 15,000/s | 15,435             | 100%   | 23 ms  | 0%     | comfortable                        |
| 20,000/s | 20,259             | 100%   | 81 ms  | 0%     | within p95<150 ms budget           |
| 30,000/s | 23,586 (plateau)   | 100%   | 336 ms | 0%     | saturated; k6 dropped 29,866 iters |

**Result: ~20,000 events/s sustained at p95 81 ms — 4× the ≥ 5,000 events/s
target**, within the < 150 ms budget. A single ingest process saturates around
23.5k events/s; the path is stateless (validate → produce to Redpanda) so it
scales horizontally by adding replicas. End-to-end verified: ClickHouse held
**3,002,328 rows** and the Redpanda consumer group `clickhouse-sink` reported
**TOTAL-LAG 0** — the async sink fully drained, at-least-once delivery intact.

Architecture note: `/v1/batch` validates + authenticates (write key) + produces
to Redpanda; a decoupled consumer batch-inserts into ClickHouse (offsets commit
only after a successful insert → at-least-once, deduped by the table engine).
ClickHouse is off the request hot path, which is why p95 stays low.

### B2. API-read latency — _not measured_

The brief's second budget (API reads p95 < 150 ms) has **no load harness** and
was not measured this run. Warm single-request SSR timings recorded earlier
(24–44 ms for dashboard routes) are encouraging but are not a p95-under-load
number. **Backlog:** add a k6 script that authenticates and exercises the
read-heavy tRPC/REST endpoints, and record p95 the same way ingestion now is.

### B3. Security

- **Secrets:** gitleaks over 290 commits — **0 leaks**.
- **SAST:** semgrep `p/owasp-top-ten` + `p/javascript` + `p/python` (ERROR
  severity) over `apps` + `packages` — **0 findings**.
- **Tenant isolation:** `@helio/db` RLS integration suite — **46/46 pass**
  (Testcontainers). Cross-tenant reads return zero rows; `helio_app` is
  `FORCE` + `NOBYPASSRLS`; tenant id is set transaction-locally.
- **Container scan:** the release pipeline Trivy-gates all 9 images on every
  tag (v2.2.3's run was green). Independent spot-scan of `helio-web:v2.2.3`
  (HIGH/CRITICAL, `--ignore-unfixed`) = **1 HIGH**: `undici 6.26.0`
  (CVE-2026-12151, WebSocket DoS) inside **npm's own vendored node_modules in
  the base Node image** — not Helio app code, a newly-disclosed 2026 CVE that
  post-dates the release scan. Low runtime risk (npm isn't invoked at runtime);
  closes when the base Node image bumps. Tracked.
- **Dependency audit (the one actionable finding — F1):** `pnpm audit --prod`
  = 5 HIGH / 7 moderate / 2 low on **production** dependencies; `pip-audit` on
  the intelligence lockfile = 1 (pydantic-settings). **Patched in PR #321**
  (hono → 4.12.27, undici override → 7.28.0, pydantic-settings → 2.14.2),
  taking the audit to 1 HIGH / 1 moderate. Tracing the highs showed the three
  `undici` ones are **not runtime-reachable**: every path is `vitest → jsdom`
  (better-auth mis-declares `vitest` as a non-dev dependency, dragging its
  jsdom→undici into the `--prod` tree) — undici is never loaded at runtime, so
  the TLS-bypass "high" was a test-tooling false-positive for exposure;
  patched regardless. See Findings.
- **Idempotency & rate limiting:** both present and exercised — the public API
  has org-scoped idempotency-key middleware; ingestion enforces a per-workspace
  fixed-window limit (verified live: excess returns `429 + Retry-After`).

### B4. Resilience

- **Backup / restore drill (live):** fingerprinted the DB (31 contacts, 3 auth
  users, `contact` RLS rowsec+forced = true), took a real `pg_dump -Fc`
  backup (511 TOC entries), **truncated `contact CASCADE` to simulate data
  loss** (→ 0 rows), restored with `pg_restore --clean --if-exists`. After
  restore: 31 contacts, 3 auth users, the same sample contact, and **RLS still
  `FORCE`d** — a restore that silently dropped FORCE RLS would be a
  tenant-isolation hole; it didn't. Backups capture auth + tenant data + RLS
  policy faithfully.
- **Worker crash / no double-send:** 34 worker tests pass, including explicit
  idempotency-across-Temporal-retries proofs for email, SMS, in-app and
  activities ("one send, one row", "SENT skipped, FAILED retried without
  duplicates"). Sends use a deterministic `journeyDeliveryId(runId, nodeId)`
  upsert, so a retry after a successful send is a no-op. Combined with
  Temporal's durable execution, a worker killed mid-journey resumes without
  lost state or duplicate sends. (A live `SIGKILL` mid-flight was not staged
  this run; the property is covered by the tests + the engine's guarantees.)
- **Dependency outage (live):** stopped ClickHouse mid-traffic — ingestion kept
  returning **202** (events buffered in Redpanda) and `/readyz` correctly
  flipped to `degraded` (`clickhouse: failed`). On restart, `/readyz` returned
  to `ok` and the buffered events **landed in ClickHouse** (sink redelivered).
  Ingestion degrades gracefully under an analytics-store outage.

### B5. Upgrade path

`prisma migrate status` = "Database schema is up to date", 93 migrations, **no
drift**. Migrations are forward-only (`prisma migrate deploy`). The specific
v2.2.2 → v2.2.3 hop carries **zero migrations** (both were bump-only releases),
so that upgrade is inherently safe. A full cross-version image upgrade with a
schema delta was not staged this run (no delta to exercise between the two
latest tags); the migration framework and clean status make the path
low-risk. **Backlog:** when the next schema-changing release lands, run an
old-release-with-data → upgrade-in-place drill and record it here.

### B6. Observability

- `/healthz` + `/readyz` on **web, api, ingest, tracking, intelligence**.
  **`workers` exposes no HTTP health endpoint** — liveness is observable via
  its Temporal task-queue poller, but a Kubernetes liveness/readiness probe
  has nothing to hit (Finding F4, Minor).
- OpenTelemetry wired in api, ingest, tracking, web; structured logging
  (pino / structlog) in all six services. Live cross-service trace propagation
  was not exercised (would need the observability profile + a multi-service
  request); the W3C-context plumbing is in code.

### B7. Deliverability & compliance

- **One-click unsubscribe:** RFC 8058 — `List-Unsubscribe` +
  `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers and a
  `/u/[token]/one-click` POST route (idempotent, no render).
- **Suppression honored:** the send recipient query filters suppressed /
  unsubscribed contacts; importer maps opted-out rows to suppressed.
- **Deliverability wizard:** SPF/DKIM/DMARC surface present (`deliverability`
  core + router + settings panel).
- **GDPR:** contact export + delete paths present.

### B8. Accessibility & i18n

- **a11y:** `a11y.spec.ts` runs axe-core with `wcag2a/2aa/21aa/22aa` tags over
  `/`, `/contacts`, `/tasks`, `/segments`, `/settings`, `/login` and **fails
  the suite on any serious/critical violation** — the exact bar the README
  claims. Backed by Radix primitives and 399 aria/role usages in app code.
- **i18n:** strings externalized via next-intl (`messages/en.json`).
- **RTL:** no direction-switching mechanism found; no RTL locale ships yet, so
  not blocking, but "RTL-safe" is not currently true (Finding F5, Minor).

## What was not done (honest limitations)

- API-read and email-send paths were not load-tested (only ingestion).
- No live OWASP ZAP run this session — the last live DAST (v2.1.0,
  `docs/security/audit-2.1.0.md`) was **0 High**, and the HTTP surface has not
  materially changed since. A fresh ZAP run is the next security pass.
- No live Temporal worker `SIGKILL` mid-journey (covered by tests + engine).
- No cross-version image upgrade drill (no schema delta between the two latest
  tags to exercise).
- Throughput is from a contended single box; treat ~20k events/s as a _floor_
  for a properly separated deployment, not a ceiling.
